# 统一奖励事件中心决策

## 背景

活动签到、任务领取和会员开通赠送已经统一通过积分服务写余额与流水，但业务入口仍分别调用活动奖励服务和会员积分赠送服务。继续增加成就、限时活动、称号或装扮后，触发、幂等和失败处理会进一步分散。

## 决策

1. 新增 `reward_event` 作为奖励事件执行与审计记录，使用业务确定的 `event_id` 全局幂等。
2. 新增显式事件协调器和策略处理器，按 `event_type` 分发活动奖励或会员开通奖励。
3. 签到和任务领取同步处理，奖励、签到/进度状态处于同一事务。
4. 会员支付成功事件在支付事务提交后处理，避免支付事务回滚但奖励已入账。
5. 现有活动加成规则和会员赠送规则继续作为规则来源，不改现有后台接口。
6. 所有星钻变化仍调用 `ITsPointsService`，并继续使用积分流水幂等键。
7. AOP 不计算奖励金额，仅允许未来用于无业务决策的审计或指标采集。
8. 管理后台提供事件分页、汇总、详情和失败重试；不允许编辑金额或删除成功事件。

## 取舍

- 不立即建立通用 `reward_rule` 表，避免一次迁移两套已投入使用的规则和管理接口。
- 不把支付后奖励放回支付事务，避免外部奖励失败阻塞已验证的会员开通。
- 失败事件既由定时任务自动扫描，也允许管理员在次数上限内手动重试。

## 影响

- 现有业务 Controller、路径、参数和返回结构不变，新增独立管理员事件接口。
- 新增一张奖励事件表和内部事件处理组件。
- 新增 Vue3 奖励事件监控页面和管理员菜单。
- 支付成功后会员奖励改为最终一致；活动领取仍为强一致。

## 回滚

恢复活动和支付 Service 的直接奖励调用，移除事件中心组件。`reward_event` 不参与积分余额计算，可保留审计或直接删除。
