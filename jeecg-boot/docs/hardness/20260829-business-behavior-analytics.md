## 目标与非目标
- 目标：仅接受十类业务事实事件，后端可信事件在事务提交后发布。
- 目标：Kafka 明细写入 ClickHouse，不再维护旧 Redis 推荐权重。
- 目标：前端接入语言、角色/故事详情浏览和受约束的推荐曝光。
- 非目标：不保留角色/故事标签，不统计停留时长，不迁移历史 MySQL 明细。

## 输入约束
- 已知上下文：现有 Kafka Producer、动态 ClickHouse 数据源和登录态采集接口。
- 强约束：用户 ID 只信任后端登录态；埋点失败不得反向影响业务。
- 禁止事项：不得改动广告事件链路，不得提交敏感配置，不得覆盖用户未提交改动。

## 任务分解
### T1 事件契约
- 输入：现有 DTO、Kafka 消息和事件目录。
- 执行动作：删除旧字段，增加事件白名单及按事件校验。
- 输出：稳定的十类事件契约。
- 验收标准：未知事件、缺失必需维度和标签字段均被拒绝。
- 证据类型：单元测试、代码检查。

### T2 后端可信触发
- 输入：角色、故事、收藏、会话、聊天和生图服务。
- 执行动作：在成功提交后发布对应事件，移除旧 AOP 注解。
- 输出：业务事实由后端可靠产生。
- 验收标准：事件不早于事务提交，关闭开关时静默跳过。
- 证据类型：单元测试、编译。

### T3 ClickHouse 明细
- 输入：Kafka 消息和 ClickHouse 动态数据源。
- 执行动作：新增 ClickHouse Mapper、消费者和初始化表。
- 输出：分析明细写入 ClickHouse。
- 验收标准：消费字段完整，部署包包含初始化脚本。
- 证据类型：Mapper 测试、脚本与打包配置检查。

### T4 前端接入
- 输入：语言切换、角色详情和故事详情页面。
- 执行动作：增加统一 API 封装和无阻塞上报。
- 输出：页面不改布局即可产生前端事件。
- 验收标准：请求失败不影响页面，事件 ID 和会话 ID 稳定生成。
- 证据类型：定向类型检查、代码检查。
